# Model Debugger Runner for PyTorch

A runner that hosts PyTorch (Hugging Face transformers) and serves the Model
Debugger Protocol (`../protocol/`) over gRPC, as the LiteRT-LM runner
(`../runner/`) does: the same RPCs, status codes and capture layout, so the
server lines its captures up with LiteRT-LM's.

It runs one model: Gemma 4 (`Gemma4ForConditionalGeneration`, eager attention),
from a Hugging Face model directory on this computer, such as Gemma 4 E2B's
snapshot. It runs on this computer only, on the CPU or the GPU (MPS on a Mac,
CUDA elsewhere).

## Layout

```
MODULE.bazel, .bazelrc      the Bazel workspace: Python 3.12, ../protocol
requirements.in             torch 2.9.0, transformers 5.17.0, ...
requirements_test.in        and its tests besides: pytest, ruff
requirements_lock.txt       both, pinned for every platform (uv --universal)
model_debugger/runner_pytorch/
  cli/runner_main.py        the command: flags, listening line, signals
  service/runner_service.py the protocol's rules around the runtime
  service/options_schema.py runtime options checked against their schema
  service/model_id.py       the model directory's id
  service/host_info.py      HostInfo, and the GPU PyTorch can use
  llm/gemma4_runtime.py     Gemma 4: load, render, feed, generate
  llm/sampler.py            greedy, temperature, top-k, top-p, seed
  llm/anchor_observer.py    each decoder layer's anchors and requested modules
  llm/execution_graph.py    execution graph of a turn's passes
  llm/capture_writer.py     the capture's files
  testing/                  pytest's main, tiny Gemma 4, test client, captures
pytorch_collector/          the capture library: collect(), to_model_explorer()
  tests/                    its tests, run by pytest under Bazel
  docs/                     its design and its plan
```

The protocol's Python messages and gRPC stubs are generated by Bazel from
`../protocol`, as the server's are; none are kept in the source tree.

## Running

```sh
cd src/runner_pytorch
bazel build //model_debugger/runner_pytorch/cli:runner
HF_HUB=~/.cache/huggingface/hub
bazel-bin/model_debugger/runner_pytorch/cli/runner \
  --model_dir "$HF_HUB/models--google--gemma-4-E2B-it/snapshots/<rev>" \
  --listen 127.0.0.1:0
```

The first build fetches Python and the pinned packages, torch among them, and
compiles gRPC's Python plugin: about two minutes. The server runs
`bazel-bin/model_debugger/runner_pytorch/cli/runner` of this checkout as its
PyTorch runner unless `--pytorch_runner` names another.

Once it listens it prints `runner: listening on port <port>`, as the LiteRT
runner does; SIGTERM or SIGINT stops it. Its cache directory is
`~/Library/Caches/model_debugger/pytorch` on a Mac, else
`${XDG_CACHE_HOME:-~/.cache}/model_debugger/pytorch`: `hashes.json`, and
`run-<pid>/turn-<n>/`, each turn's capture until it is released or the runner
exits.

The check, also part of `ci/check_all.sh`: buildifier, ruff (with
`../server/ruff.toml`), then `bazel test //...`:

```sh
[RUNNER_PYTORCH_MODEL=/path/to/gemma-4-E2B-it] ci/check_runner_pytorch.sh
```

The tests use pytest, run by Bazel (`testing/test_main.py`). Without
`RUNNER_PYTORCH_MODEL` the real model's test (`cli:runner_main_test`) is
skipped; `RUNNER_PYTORCH_DEVICE` (`CPU` or `GPU`) and `RUNNER_PYTORCH_DTYPE` (a
`dtype` option) choose how it loads. Bazel passes the three on (`.bazelrc`). The
tests that check captures with the server's capture index import it from
`../server`, outside Bazel's view, so they run every time, as does the real
model's.

## pytorch-collector

The intermediate tensors are captured by pytorch-collector's `collect()`, the
user's capture library, which lives here, in `pytorch_collector/`
(`//pytorch_collector`), the one source of it from now on: moved on 2026-10-20
from the user's repository `~/Projects/pytorch-collector`, commit `fe82ff9` with
its module-only capture (`collect(model, modules=[...])`, which the runner's
`anchor_observer` needs) not yet committed there. The package is that working
tree's `src/pytorch_collector/` byte for byte, but for its `equivalence` checks
(Z3 and tflite against LiteRT), which stayed there with the examples. Its
README, design and plan came with it, and its tests: `bazel test
//pytorch_collector/...` (see `pytorch_collector/README.md`). It keeps its own
code style, so ruff checks `model_debugger/` only. The wheel holds the package
`pytorch_collector` beside `model_debugger`, for it is on no index to require.

The packages are pinned for every platform at once by uv, which Bazel fetches:

```sh
bazel run //:requirements.update
```

## The model and its id

The runner takes no upload: `UploadModel` fails with `FAILED_PRECONDITION`. It
loads the directory it was started with, whose id is the sha256 of its manifest;
`Load` of any other sha256 is `NOT_FOUND`. The manifest has one line per file,
sorted by path (as code points):

```
<relative path>\t<size>\t<sha256 of the file's bytes>\n
```

The files are every path under the directory, at any depth, that is a regular
file or a symbolic link to one (a snapshot links into its blobs), but none with
a path component starting with `.`; paths use `/`. The id is the sha256 of the
manifest's UTF-8 bytes, lower-case hex. The runner computes it in the background
at start, keeping each file's hash in `hashes.json` by resolved path, size and
modification time; `Load` waits for it.

## The protocol

- `GetInfo`: runtime `PYTORCH`, version `torch <v>, transformers <v>`; the host
  as the system reports it; `gpu` set when MPS or CUDA is available. Load
  options: `dtype` (`default`, the checkpoint's, `float32`, `float16`,
  `bfloat16`), `cpuThreads`, `observe` (`none`, the default, or `anchors`),
  `observeMemoryLimitBytes` (collect()'s budget for one turn, by default 8 GiB)
  and `observeModules` (the modules to capture beside the anchors, each
  `{"module": <path>, "edge": "in" | "out"}`; the server fills it, and a Load
  naming a module the model has not fails); chat options: none.
- `Load`: start token `<bos>` when the chat template starts with it; stop tokens
  and sampler defaults from `generation_config.json`.
- `CreateChat`: earlier messages; greedy when `top_k` is 1 or `temperature` is
  0; unset options are the model's defaults; `seed` seeds the sampling. It
  closes the chat there is first, as the LiteRT runner does.
- `Send`: the chat rendered with the tokenizer's chat template, fed as LiteRT-LM
  feeds it (see `llm/gemma4_runtime.py`): one prefill pass over the new
  positions but the last, labelled step n; decode step k feeds position k - 1;
  the last token generated is held back and fed first next turn. The cache is
  kept when the rendering starts with what it holds and the held token; else the
  turn replays from position 0. No thinking.
- `ReadCaptures`, `ReleaseCaptures`: as the LiteRT runner.

## The capture

One safetensors file per tensor per pass,
`<signature>_<key>_step_<step>.safetensors`, `__metadata__` `{signature:
prefill|decode, step: <n>}`, the tensor in its own dtype (BF16 for a BF16
model):

- `prefill_pre_input_pos_step_<n>`, `decode_pre_input_pos_step_<k>`: the
  positions fed, int32;
- `decode_post_logits_step_<k>`: the one row of logits that produced the step's
  token;
- `(pre|post)_kv_cache_(k|v)_<layer>`: before and after the prefill, and after
  the last decode step; `[batch, kv_head, sequence, head_dim]`, which the
  metadata `layout: k:bhsd,v:bhsd` says; a sliding window layer holds only its
  last positions, which `kv_positions: <first>-<last>` names. Gemma 4's
  KV-shared layers (15 to 34 of E2B) have no cache and no file;
- `generated_tokens.jsonl`: one line per released token, `{"token_ids": [[id]],
  "texts": [text]}`; a stop token is not released.

## The anchors

A model loaded with `observe: anchors` runs each turn's forward passes inside
one pytorch-collector `collect()` (`llm/anchor_observer.py`), under
`torch.no_grad()`: collect() refuses `torch.inference_mode()`, so every turn
runs under no_grad, observed or not. Of its records only each decoder layer's
four anchors are written, per forward pass: the layer's input and output, and
the output of each block of the layer, which ends at the anchor that names it in
the skeleton (transformers 5.17.0, `Gemma4TextDecoderLayer.forward`, lines
1384-1441):

-   `input` (): what `model.language_model.layers.<i>` reads, argument 0
-   `intermediate.1` (Attention): what `layers.<i>.pre_feedforward_layernorm`
    reads
-   `intermediate.2` (Feed Forward): what `layers.<i>.per_layer_input_gate`
    reads
-   `output` (Per-Layer Embedding): what `layers.<i>` returns, after
    `layer_scalar`

and, of each module the Load asks for (`observeModules`), what it reads (`in`,
argument 0) or returns (`out`): the server asks for the modules of the semantic
operators it pairs with LiteRT-LM points chosen (layer 3's `self_attn.q_proj`,
say).

Each anchor is
`<signature>_post_anchor_<layer>_<anchor>_step_<step>.safetensors`, each module
`<signature>_post_module_<module path>_<edge>_step_<step>.safetensors`, the
collector's clone as the model holds it (an anchor `[1, rows, hidden]`, rows the
positions the pass fed), in its own dtype, its metadata naming besides the
signature and step the `module`, `edge` and `path` in the collector's record,
and an anchor's `layer` and `anchor`. Beside them `observation.json`: `{observe,
capture, modules, memory_limit_bytes, captured, reason, snapshot_bytes,
execution_graph, execution_graph_reason}`.

A turn is captured in one of two ways (`capture`):

- `full`, the first observed turn of a Load on the CPU: `collect(model,
  memory_limit_bytes=...)`, every module's and every operator's inputs and
  outputs, on the CPU only. Only such a capture can export the execution graph
  (`llm/execution_graph.py`), which the turn's capture holds as
  `execution_graph.json.gz`: of the first pass of each signature it ran, the
  graph pytorch-collector's own `to_model_explorer(capture, hide_unused=True)`
  draws (one node per ATen operator call under its module path, parameters as
  attributes, what the pass read from outside as `inputs`), and the class of
  each module the operators ran in (`modules`); `execution_graph` names the
  signatures it holds. Nothing is folded here: the server keeps the graph per
  model and draws it (src/server, `graph/pytorch_graph.py`). For Gemma 4 E2B it
  takes about 0.13 s to export and is 0.2 MB gzipped (prefill 5,307 nodes,
  decode 5,272).
- `modules`, every other observed turn, and every one on the GPU (MPS):
  `collect(model, memory_limit_bytes=..., modules=[...])`, hooks only on the
  modules the anchors and the modules asked for are taken at, no operator
  observed, snapshots kept on the device the model runs on; the same tensors,
  bit for bit, in a fraction of the time and memory. It still snapshots each
  selected module's whole inputs: a layer's arguments carry the KV cache, saved
  again at every layer, which is most of it, and grows with the context. A Load
  whose first turn did not export the graph (its capture failed) exports none.

A forward pass whose capture fails is run again without it from the KV cache it
started from (the cache's layers rebind their tensors, never write them in
place, so those held before the pass are as they were), the rest of the turn
runs unobserved, and the turn completes with no tensors: `captured` false,
`reason` collect()'s words, as past the budget, `MemoryError: Snapshot memory
limit exceeded at <path>`.

Measured on an Apple M2 Max (64 GB) with Gemma 4 E2B in BF16, two turns of "Name
three colors." (13 and then 50 prompt tokens as this runner renders them, 24
reply tokens each: one prefill and 24 decode passes), greedy, a runner process
each:

-   CPU, observe none (2.4 s): 2.4 s: 5.2, 5.2 GB:
-   CPU, observe anchors (16.2 s, full, graph): 4.2 s, modules: 10.5, 10.7 GB:
    4.57, 1.10 GB
-   CPU, anchors and 4 modules (16.4 s, full, graph): 4.3 s, modules: 10.5, 10.7
    GB: 4.57, 1.10 GB
-   MPS, observe none (3.3 s): 3.0 s: 0.9, 1.0 GB:
-   MPS, observe anchors (7.1 s, modules): 6.3 s, modules: 0.9, 1.0 GB: 0.44,
    1.10 GB
-   MPS, anchors and 4 modules (6.5 s, modules): 7.4 s, modules: 0.9, 1.0 GB:
    0.44, 1.10 GB

Each observed turn writes 3,500 anchor files (140 per pass), and 100 module
files with the four modules asked for (layer 3's q_proj, o_proj and down_proj,
layer 20's gate_proj). The CPU's second turn starts at the RSS the full first
turn left (10.4 GB; the allocator keeps it), and adds 0.3 GB. (RSS, sampled
every 20 ms; the weights are mapped from the files and count as they are read.
On MPS the weights and the snapshots are in the GPU's memory, which RSS does not
count.)
